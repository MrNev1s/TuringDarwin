# TuringProbe 0.5.1 — complete offline TU116 MMU validation

## Status

**OFFLINE RESEARCH PASS. ZERO DEVICE ACCESS. NO HARDWARE BOOT AUTHORISED.**

0.5.1 converts the earlier format model into a broader deterministic validation
system. The kext hardware interface remains unchanged from 0.4.0.

## Source-backed architecture

The model keeps the established TU102/TU116 profile:

- 47-bit physical/DMA address profile;
- 49-bit GPU virtual address hierarchy;
- page sizes 4 KiB, 64 KiB and 2 MiB;
- root/PDE3: 2 index bits;
- PDE2: 9 bits;
- PDE1: 9 bits;
- dual PDE0: 8 bits and 16-byte entries;
- 4 KiB leaf: 9 bits / 512 entries;
- 64 KiB leaf: 5 bits / 32 entries;
- direct 2 MiB PTE in the low half of PDE0;
- low PDE0 half for 64 KiB and high half for 4 KiB;
- 16 logical kinds with invalid kind 0x07;
- no-GSP fallback from compressed logical kinds to uncompressed kinds;
- compression/comptagline blocked without an authorised firmware path.

Primary references:

- Nouveau `tu102.c` for DMA width and kind map;
- Nouveau `vmmgp100.c` for hierarchy, PTE/PDE construction and instance flags;
- Nouveau `vmmtu102.c` for the operational invalidation sequence;
- NVIDIA Open UVM `uvm_turing_mmu.c` as an independent hierarchy and field
  cross-check.

## Fixed golden vectors

`research/mmu-golden-vectors.json` contains non-random expected values for:

- 4 KiB, 64 KiB and 2 MiB virtual-address decomposition;
- video and system PTEs;
- no-GSP kind fallback;
- a maximum 47-bit-aligned physical address;
- video and coherent-system PDEs;
- VER2/64-KiB instance PDB flags.

The test compares exact 64-bit words, then decodes them back to their original
fields. These vectors prevent a random round-trip test from accepting matching
encoder/decoder mistakes.

## Multi-page address-space builder

`research/tu102_address_space.py` adds a deterministic synthetic allocator and
constructs full byte images for multiple mappings.

Validated cases:

- 1024 consecutive 4 KiB pages crossing a 2 MiB leaf boundary;
- 64 consecutive 64 KiB pages crossing a 2 MiB leaf boundary;
- 300 consecutive 2 MiB pages crossing a 512 MiB PDE0-table boundary;
- two 4 KiB mappings crossing the 128 TiB root-index boundary;
- disjoint 4 KiB and 64 KiB mappings in the two halves of one PDE0 region;
- explicit physical alias opt-in;
- rejection of virtual overlaps across different page sizes;
- deterministic table allocation and digesting;
- missing-table and corrupt-chain rejection.

The builder and walker share entry-format helpers but do not share a stored
translation result. The walker follows the generated bytes from the root and
reconstructs the physical address.

## Promotion and demotion

The model supports a strict offline transformation:

```text
512 contiguous 4 KiB mappings
→ one direct 2 MiB PDE0 PTE
→ 512 restored 4 KiB mappings
```

Promotion requires:

- 2 MiB-aligned virtual and physical bases;
- all 512 pages present;
- contiguous physical pages;
- identical aperture, kind and protection attributes.

After demotion, the deterministic page-table digest must equal the original
4 KiB image. Non-contiguous pages or differing attributes fail closed.

## Alias and overlap policy

Virtual overlap is always rejected. Physical aliasing is rejected unless the
caller explicitly passes `allow_alias=True` for the new mapping. This keeps
future tests from accidentally hiding duplicate ownership of the same physical
memory.

## Transaction model

`research/mmu_transaction_plan.py` defines the future sequence without
implementing any operation:

```text
safe baseline
→ host allocation
→ table build
→ table verification
→ stage device memory
→ build instance block
→ program PDB
→ invalidate TLB
→ verify translation
```

Every step records:

- source and destination phase;
- whether it touches or writes the device;
- required evidence;
- timeout;
- inverse operation;
- inverse proof status.

All CPU-only failure points successfully simulate rollback to the safe baseline.
The first hardware step remains blocked because VRAM allocation, write/readback,
and its inverse have not been proven.

## Test totals

The complete suite currently includes:

- 60,000 virtual-address split/compose vectors;
- 60,000 randomized PTE/PDE vectors;
- 30,000 complete single-image build/walk vectors;
- fixed golden vectors;
- 12,025 sampled translations through multi-page images;
- promotion/demotion and conflict cases;
- failure injection at every offline transaction phase;
- all legacy PCI/MMIO/PTOP/FB contracts.

## CI integration

`tools/run-offline-validation.sh` is the single validation entry point. Both
GitHub Actions and `tools/build.sh` invoke it. Therefore a kext artifact cannot
be built successfully while omitting the MMU suites.

The workflow also triggers on `research/**` and packages the complete validation
log.

## Proof boundary

0.5.1 proves that the software model is internally consistent, source-backed,
and fail-closed for the tested cases. It does not prove:

- real VRAM allocation;
- CPU writes into VRAM;
- page-table placement accepted by the GPU;
- instance-block ownership;
- PDB programming;
- TLB invalidation;
- fault reporting;
- translation by a real engine;
- DMA or command submission.

The MMU hardware whitelist remains empty.
